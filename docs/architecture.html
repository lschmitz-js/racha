Racha de Segunda — Architecture

A small webapp for Monday-night 5-a-side soccer: balanced 3-team draws, a 5-minute match clock, live event tracking, winner-stays rotation, and a season recap. Single Docker container, single SQLite file, deployable anywhere.

System overview

The big idea: one Docker image with one mounted volume. The same artifact runs on AWS, GCP, or your future Proxmox box — only the host machine changes.

Stack at a glance

Frontend

Vite + React + TypeScript

Tailwind for styling. TanStack Query for server state. wouter for routing (~1 kB router instead of react-router). PWA manifest so iOS treats it as a native app.

Backend

Hono on Node.js 20

Minimal HTTP framework. Same process serves /api/* and the SPA static build — single origin, no CORS gymnastics.

Database

SQLite (better-sqlite3)

Single file at /data/racha.db. WAL mode for concurrent reads. Backs up by copying one file.

Shared types

Zod + TypeScript

One package @racha/shared consumed by both frontend and backend so request/response shapes can't drift.

Reverse proxy

Caddy 2

Terminates TLS. Auto-fetches Let's Encrypt cert and renews it. 4 lines of config in Caddyfile.

Container

Docker + docker-compose

Multi-stage build, ~355 MB image, ~3-second cold boot. Two services: racha + caddy.

Hosting

GCP Compute Engine

e2-micro instance in us-central1-a — always-free tier. Static IP optional, costs $0.

Source

GitHub

lschmitz-js/racha. Deploys are git pull && docker compose up -d --build.

Yes, there's a database — here's the schema

SQLite, ~75 KB on disk for an empty install. Eight tables, all keyed on text IDs (compatible with the legacy app's mo7… format). Times stored as Unix milliseconds.

TableWhat it holdsNotable fields
players Master roster (season + drop-ins) type (season/dropin), role (player/gk), skills_json (8 ratings 1–5)
sessions One Monday night date, status (draft/live/done)
session_players Who showed up that night join table
session_teams The 3 teams drawn for the night (white/black/green) vest
session_team_players Lineup per team join table
matches One 5-minute game inside a session elapsed_ms (canonical clock), status, result, winner_team_id
match_players Starting lineup for a match starting (1 = on the pitch at kickoff)
match_events The event log — every goal, assist, sub, etc. type, clock_ms, link_id (pairs goal↔assist and sub_in↔sub_out)
Everything funnels through match_events. Goals, assists, beautiful plays, silly mistakes, bad plays, GK saves, and substitutions are all rows in one table. The season recap is just a few GROUP BY queries against it.

Why SQLite instead of Postgres?

  • Backup is cp racha.db. No pg_dump, no port to expose.
  • One process, no daemon. Lower idle memory on a free-tier VM.
  • Scale fits the workload. 24 players × 30 weeks × 5 matches × 20 events ≈ 75 k rows/season. SQLite scans that in single-digit milliseconds.
  • Trivially portable to Proxmox. Just move the data/ folder. No DB migration.

What happens when you tap "Goal"

  1. SPA generates a UUID client-side and POSTs to /api/events with { id, match_id, type: 'goal', player_id, team_id, link_id }.
  2. Hono looks up the match, computes the current clock from elapsed_ms + (now − started_at), and inserts the event with that clock_ms.
  3. Insert is idempotent on the client UUID — a retry over flaky cellular doesn't double-count.
  4. SPA shows a 4.5-second toast: "Joao ⚽ — tap a teammate for assist?" Tapping a teammate posts a paired assist event with the same link_id as the goal.
  5. Undo deletes by link_id, so one tap reverts both rows.

What's deliberately not in the picture (yet)

  • Auth No login. Obscure URL only. Add a RACHA_TOKEN env var if you ever want to gate writes.
  • CDN Caddy serves assets directly. The free-tier VM handles this fine for < 100 users; revisit if traffic explodes.
  • Continuous backup litestream.yml is committed but not running. When you self-host on Proxmox, point it at a NAS share.
  • CI/CD No GitHub Actions yet. A workflow that builds and pushes to GHCR on every main commit would shrink VM rebuild time from 4 minutes to 10 seconds.
  • Monitoring No metrics or uptime checks. A free Uptime Robot ping at /api/health is the cheapest add-on.
